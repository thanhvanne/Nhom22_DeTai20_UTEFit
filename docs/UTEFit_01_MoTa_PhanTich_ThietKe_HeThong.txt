2. Tổng quan đề tài và mục tiêu
2.1. Tên đề tài
“Xây dựng website quản lý chuỗi phòng tập thể thao UTEFit bằng Spring Boot + Thymeleaf + Bootstrap + JPA + MySQL + JWT + WebSocket + Cloudinary.”
2.2. Bài toán
UTEFit quản lý nhiều chi nhánh phòng tập trên một hệ thống thống nhất. Người dùng có thể xem chi nhánh, gói tập, lớp và PT; hội viên đăng ký gói, thanh toán, đặt lớp, tương tác với PT, check-in và đánh giá; PT xử lý yêu cầu, lịch cá nhân và chat; Admin quản trị toàn chuỗi và xem thống kê.
2.3. Mục tiêu chính
• Xây dựng ứng dụng web theo đúng mô hình 3 tầng và thể hiện rõ trách nhiệm Controller – Service – Repository.
• Đảm bảo logic, validation và security ở backend; không tin dữ liệu do frontend tự khai báo.
• Thể hiện 4 actor rõ ràng: Guest, Member, PT, Admin; Manager chỉ là mở rộng.
• Tạo chuỗi nghiệp vụ có đầu–cuối để demo: đăng ký → OTP → membership → payment → lớp → PT → lịch/chat → check-in → review → thống kê.
• Có lịch sử GitHub và bằng chứng AI rõ ràng, thể hiện mỗi thành viên hiểu và làm chủ phần code của mình.
• Ưu tiên chức năng ổn định và tích hợp được hơn số lượng chức năng rời rạc.

8.1. Nguyên tắc dữ liệu
• User là bảng tài khoản chung; role = MEMBER/PT/ADMIN. PT có thêm Trainer profile; Admin không cần bảng Admin riêng.
• WebSocket không thay thế database: Conversation/Message vẫn lưu MySQL.
• Ảnh/video không lưu binary vào MySQL; chỉ lưu URL/public_id Cloudinary.
• Không xóa cứng dữ liệu nghiệp vụ quan trọng nếu sẽ làm mất lịch sử; dùng active/status/soft-delete khi phù hợp.
• Các enum/status phải chốt sớm để tránh mỗi người dùng một chuỗi khác nhau.

9. Security – Validation – Error Handling
9.1. Authentication
Để vừa đáp ứng tên đề tài có JWT vừa phù hợp website Thymeleaf, hướng khuyến nghị là Spring Security xác thực JWT qua cookie HttpOnly. Token không nên được đọc/ghi tùy tiện bằng JavaScript. Với form POST dùng cookie, cần giữ cơ chế CSRF phù hợp của Spring Security thay vì tắt toàn bộ chỉ để “cho chạy”.
9.2. Authorization
/public/**              → permitAll
/member/**              → ROLE_MEMBER
/pt/**                  → ROLE_PT
/admin/**               → ROLE_ADMIN
 
Ngoài role-level còn phải kiểm tra ownership:
PT A không được sửa request/lịch của PT B.
Member A không được đọc conversation của Member B.
9.3. Validation nhiều lớp
LớpVí dụDTO/Bean Validation@NotBlank, @Email, @Size, @Pattern, @Min, @Max.Service business ruleEmail unique; membership active; capacity; overlap; state transition.Database constraintUNIQUE email/code; FK; NOT NULL; index.SecurityRole + ownership + CSRF/JWT validation.UIHiển thị lỗi thân thiện; không dùng UI validation thay backend.
9.4. Error handling
Nên có GlobalExceptionHandler cho validation error, business exception, access denied và lỗi hệ thống. Không hiển thị stack trace, secret hoặc thông tin nhạy cảm cho người dùng.

12. Kiểm thử và chất lượng
12.1. Definition of Done cho mỗi chức năng
• Code đúng 3 tầng; không Controller→Repository.
• Có server validation + business rule + security/ownership.
• Có giao diện chạy được và responsive cơ bản.
• Có dữ liệu demo và happy path chạy từ UI đến DB.
• Có ít nhất 1 test lỗi/edge case thủ công; chức năng quan trọng nên có unit/integration test nếu kịp.
• Có commit rõ + PR + người khác review.
• Có ảnh/chứng cứ cho báo cáo: activity/sequence, source, UI, test result, prompt log.
12.2. Integration checkpoints
CheckpointLuồng phải chạyCP1 – AuthRegister → OTP → Login → Role redirect.CP2 – MemberMembership → Payment/CASH → Class Booking → Schedule.CP3 – PTMember Request → PT Accept → Create Schedule.CP4 – RealtimeChat/Notification realtime + reload có history.CP5 – AdminCreate Branch/Plan/Class/Schedule → Check-in → Statistics.CP6 – Full flowGuest → Member → PT → Admin, chạy trên cùng database và cùng codebase.
