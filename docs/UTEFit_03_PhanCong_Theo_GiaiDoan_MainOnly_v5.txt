0. CÁCH ĐỌC TÀI LIỆU NÀY
Tài liệu này cố tình bỏ cách trình bày kiểu bảng dependency phức tạp. Cả nhóm chỉ cần đi từ Giai đoạn 0 đến Giai đoạn 8. Trong mỗi giai đoạn, đọc đúng phần tên mình rồi làm theo thứ tự được ghi.
Nguyên tắc dễ nhớ: A dựng nền và làm Guest/Member. B làm PT và mọi thứ có PT tham gia. C làm toàn bộ chức năng Admin. Ba người được code cùng lúc khi không đụng cùng file; nhưng mỗi lần push lên main chỉ có một người push.
0.1. Chuỗi sản phẩm cuối cùng
Guest -> Register -> OTP -> Login
      -> Member -> Membership -> Payment -> Class Booking
      -> Tìm PT -> Gửi Request -> PT Accept/Reject
      -> Tạo lịch Member-PT -> Chat WebSocket -> Notification
      -> Check-in -> Review
      -> Admin quản lý toàn hệ thống -> Statistics
0.2. Cách dùng main mà vẫn ít conflict
1. Đầu buổi: cả ba người đều chạy git checkout main và git pull origin main.
2. Mỗi người chỉ sửa phần mình được giao. Không tự ý sửa file owner của người khác.
3. Khi sắp push, nhắn nhóm: "A/B/C chuẩn bị push, mọi người tạm đừng push".
4. Người push chạy git pull origin main thêm một lần, chạy lại project/test, sau đó mới git push origin main.
5. Push xong nhắn "PUSH DONE". Hai người còn lại lập tức git pull origin main rồi mới tiếp tục.
6. Không dùng git push --force. Có conflict mà không chắc thì dừng và gọi đúng owner file xử lý.
Quy tắc quan trọng: Code có thể song song. Push lên main phải tuần tự từng người một.
0.3. File dùng chung ai được quyền quyết định?
• A sở hữu: pom.xml ở giai đoạn nền, SecurityConfig, auth/security, User/OtpCode, Membership, Payment, Review, layout/fragments dùng chung.
• B sở hữu: Trainer, TrainerRequest, PersonalTrainingSchedule, Conversation, Message, Notification, WebSocketConfig, CloudinaryService.
• C sở hữu: Branch CRUD nghiệp vụ Admin, MembershipPlan/Category/FitnessClass/ClassSchedule quản trị, Promotion, Checkin, Admin Statistics.
• Nếu cần sửa file của người khác: nhắn người owner sửa hoặc cả hai thống nhất một lượt sửa. Không âm thầm sửa rồi push.
